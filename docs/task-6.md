## Отчет

### Dockerfile

В `Dockerfile` описывается процесс `multi-stage` сборки. Конкретно в моем экземпляре
на этапе `build` производится установка зависимостей и сборка статических файлов.

На этапе `production` действий больше:

- Объявление метаданных.
- Объявление порта.
- Описание Health Check.
- Установка зависимостей (`curl` и `libpq5`).
- Добавление пользователя.
- Копирование статики, исходников и скрипта входа из `build` этапа.
- Запуск.

Сборка запускается командой:

```bash
docker buildx build --platform linux/amd64 -t fefu-django-app:1.0.0 .
```

Попробовал использовать движок `Buildx` - кэширование сокращает время на тесты.

Для того, чтобы запушить образ в реестр, нужно выполнить пару команд:

```bash
docker tag fefu-django-app:1.0.0 digit4lsh4d0w/web-2025:1.0.0
docker tag fefu-django-app:1.0.0 digit4lsh4d0w/web-2025:latest
docker push digit4lsh4d0w/web-2025:1.0.0
docker push digit4lsh4d0w/web-2025:latest
```

Я просто изменяю название образа (через присваивание тега) и пушу в облако.
Таким образом в моем реестре хранятся образы с конкретным тегом и `rolling` тегом.

### Entrypoint

В скрипте входа `docker-entrypoint.sh` я просто выполняю миграцию по запросу
и запускаю сервер.

По ходу изучения темы узнал о проблеме `1 PID`, при котором процесс, порождаемый в
контейнере в результате `CMD` не отвечает на сигналы `SIGINT` и `SIGTERM`.

У меня первым процессом является `gunicorn`, но он корректно обрабатывает сигналы.

### Compose

С `Docker Compose` я знаком не по наслышке. 50+ поднятых сервисов в разных проектах.
По безопасности париться не хотелось, поэтому все работает от дефолтных пользователей,
указанных в сценариях сборки.

Выставляем `healthcheck` там, где их не хватает. Проставляем переменные среды для БД
и проекта на `Django` (секреты тоже в переменных среды, но тут сойдет).
Создаем общий том для статики, шарим между `Nginx` и проектом.
Для `Nginx` отдельно прокидываем конфиг, отдельно пересобирать не нужно.

Кстати, образ залил в свой [Docker Hub](https://hub.docker.com/repository/docker/digit4lsh4d0w/web-2025).

### Развертывание

У меня ВМка на `Debian 13`. Установка `Docker` и `Docker Compose` производится по
официальной инструкции. Для развертывания моего проекта достаточно иметь два файла:

1. `docker-compose.yml`
2. `nginx.conf`

Они скачиваются с [GitHub](https://github.com/digit4lsh4d0w/fefu-web-2025/tree/a48b4ad7a51f4ae5b5b06b18d0c171d5c03af7c7/deploy/compose).

Ну а дальше простая команда:

```bash
docker compose up -d
```

Процесс развертывания можно увидеть в видео ниже.

Ну а вот вывод команды `docker images`:

```plaintext
digit4lsh4d0w/web-2025:1.0.0   fa4563e6e852        272MB         60.4MB    U
nginx:1.29-alpine              b0f7830b6bfa       93.1MB         26.8MB    U
postgres:18-trixie             5773fe724c49        649MB          168MB    U
```

Мой образ, конечно, жирноват. Причина отчасти в исходном образе, отчасти из-за зависимостей.
Пытался пооптимизировать через `dive`, но особо сильно образ не уменьшил.

Вот еще вывод команды `docker compose ps`:

```plaintext
STATUS                    PORTS
service-db-1      postgres:18-trixie                       "docker-entrypoint.s…"   db        51 minutes ago   Up 51 minutes (healthy)   5432/tcp
service-nginx-1   nginx:1.29-alpine                        "/docker-entrypoint.…"   nginx     51 minutes ago   Up 51 minutes (healthy)   0.0.0.0:80->80/tcp, [::]:80->80/tcp
service-web-1     docker.io/digit4lsh4d0w/web-2025:1.0.0   "./docker-entrypoint…"   web       51 minutes ago   Up 51 minutes (healthy)   80/tcp
```

Порты, кстати, прокинул только для `Nginx` - все остальное связывается через мосты `Docker`.

### Заключение

Ну вот, собственно, и все. Попробовали `Django` и, честно говоря, больше я к этой дичи не вернусь.
Типизации нет, почти все ошибки вылазят в рантайме. Структура импортов мне в `Python` понятнее не
стала. Стандартный скрипт `Django` генерирует проект и приложения в корне репозиторий, а я все
перенес в `src`. Делать `src` корнем проекта, создавая файл `__init__.py` мне не нравится - не
консистентно, да и просто тупо. При этом, запуская `gunicorn` нужно указывать именно путь по
структуре импортов. Таким образом приходится обявлять `src` как рабочую директорию.

Основная претензия, конечно, к двум вещам:

- Отсутствие типизации или псевдотипизация, на которую ругаются линтеры.
- 80% ошибок находятся в стадии рантайма. Пока руками не натыкаешь - не узнаешь.
  Покрывать тестами - боль, т.к. ответ может быть 200, а ты в шаблон данных не дал.

Для себя я сделал выводы - `Django` в проде, это либо что-то простое, либо следствие большого
количества обученных программистов. Гораздо лучше было бы разделить бэк и фронт.
